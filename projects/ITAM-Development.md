# 삼성물산 ITAM 자산관리시스템 TO-BE 전환 구축 프로젝트

## 1. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 프로젝트명 | ITAM 자산관리시스템 TO-BE 전환 구축 |
| 수행 기간 | 2025.12 ~ 2026.06 |
| 담당 업무 | ITAM 화면 및 기능 구현, SQL 변환, SLA 통계 시스템화 |
| 기술 스택 | E-GENE(No-code 플랫폼), JavaScript, JSP, Java, MariaDB |
| 협업 도구 | GitLab |


### 프로젝트 소개

기존 X-Platform·Java 기반 ITAM 자산관리시스템을 E-GENE(No-code) 플랫폼으로 전환하는 프로젝트입니다.

기존 ITSM은 E-GENE 플랫폼으로 운영되고 있었으며, 기존 ITAM을 동일한 플랫폼 환경으로 전환하여 운영 중인 ITSM 시스템과 연계하는 것을 목표로 진행했습니다.

기존 시스템의 화면과 SQL을 참고하여 E-GENE 플랫폼에 맞게 화면을 구성하고, 관련 기능과 데이터 처리 로직을 구현했습니다.

※ 기존 ITSM 시스템 개발은 담당 범위에 포함되지 않으며, ITAM 자산관리 기능의 전환 및 구현을 담당했습니다.

## 2. 담당 업무

### 2-1. AS-IS 화면 확인 및 TO-BE 화면 구현

- 기존 X-Platform 기반 ITAM 화면 확인 및 기능 구성 파악
- E-GENE 플랫폼에서 구현 가능한 형태로 화면 구성
- 현장 네트워크 신청 및 관리 화면 구현
- 재고 현황 화면 구현
- 개인정보 신청 관리 화면 구현
- 주로 관리자 페이지를 담당하고, 사용자 페이지 중 현장 네트워크 신청 화면 구현
- 화면별 목록, 상세 조회, 데이터 처리 기능 구현

### 2-2. SQL 변환 및 데이터 구조 반영

- 기존 Tibero SQL을 MariaDB 문법에 맞게 수정
- 기존 화면에서 사용하던 조회 SQL을 TO-BE 테이블 구조에 맞게 변환
- 신규 테이블 및 컬럼 구조에 따른 SQL 수정
- E-GENE 플랫폼에서 사용하는 정해진 컬럼 구조에 맞춰 데이터 변경 사항 확인 및 요청
- 화면 기능에 필요한 데이터 조회 및 처리 로직 반영

### 2-3. SLA 통계 시스템화

- 협력사별 ITSM 요청 및 처리 현황을 확인할 수 있는 통계 기능 구현
- 기존 수작업으로 집계하던 SLA 데이터를 시스템에서 관리할 수 있도록 기능 구성
- 협력사별 처리 시간 및 통계 데이터 입력·조회 화면 구현
- 다른 시스템과 API 통신을 통해 필요한 데이터 수집
- JSP를 활용한 API 호출 및 데이터 수집 로직 구현
- 배치 작업을 통해 수집한 데이터를 데이터베이스에 적재하는 기능 구현

### 2-4. 테스트 및 배포

- 구현한 화면 및 기능 단위 테스트
- 오류 수정 및 기능 보완
- 통합 테스트 및 인수 테스트 대응
- 테스트 결과에 따른 수정 사항 반영
- 운영 배포 지원

## 3. 주요 어려움 및 해결 과정

### 3-1. 새로운 No-code 플랫폼에 대한 적응 및 활용 방법 습득

**어려웠던 점**

프로젝트에서 처음 사용하는 E-GENE(No-code) 플랫폼으로 개발을 진행하면서 기존에 경험했던 일반적인 웹 개발 방식과 다른 구조 및 사용 규칙을 익히는 데 어려움이 있었습니다.

- 화면 새로고침 등 플랫폼에서 제공하는 별도의 공통함수 사용 필요
- 폼 내부뿐 아니라 릴레이션 영역에도 별도의 JavaScript 로직 작성 필요
- 특정 데이터에 접근하기 위해 플랫폼에서 제공하는 공통함수 활용 필요
- JSP 작성 시 플랫폼 고유의 규칙에 따라 데이터 조회 및 반복문 처리
- 목록에서 바로 수정하는 기능이 제한되어 상세페이지를 별도로 구성하는 등 플랫폼의 제약에 맞춘 화면 설계 필요

기존 JavaScript나 JSP 작성 방식만으로 해결하기 어려운 부분이 있어 플랫폼의 구조와 규칙을 이해하는 과정이 필요했습니다.

**해결 과정**

- 플랫폼 업체에서 제공하는 교육을 수강하며 기본 구조와 사용 방법 학습
- 실제 개발 중 발생한 궁금한 점을 정리하여 추가 교육에 참여하고 직접 질문
- 업체에서 운영하는 개발자 카페와 공식 게시판을 활용해 해결 방법 탐색
- 기존 E-GENE 프로젝트에 구현된 소스 코드하여 를 참고유사한 기능의 구현 방식 확인
- 같은 팀에서 근무한 플랫폼 업체 담당자들과 지속적으로 소통하며 기능 구현 방법과 제약 사항 확인

특히 처음에는 해결 방법을 찾기 어려웠던 화면 새로고침이나 데이터 접근 방식 등도 기존 소스와 커뮤니티 자료를 찾아보며 플랫폼에 맞는 방법을 익혀 적용했습니다.

**배운 점**

처음 접하는 기술이나 개발 환경에서는 기존에 알고 있던 방식만으로 문제를 해결하기 어렵다는 점을 경험했습니다.

이를 통해 필요한 지식을 스스로 찾아 학습하는 것뿐 아니라, 공식 교육과 기술 문서, 커뮤니티, 기존 소스 코드, 동료와의 소통 등 다양한 경로를 활용해 해결 방법을 탐색하는 **자기주도적 학습 및 문제 해결 역량**을 키울 수 있었습니다.

또한 기술의 특성과 제약 사항을 이해하고 그 환경에 적합한 구현 방법을 찾는 것이 중요하다는 점을 배웠습니다.

### 3-2. 개발 초기 분석 및 공통 기준 정의의 중요성

**어려웠던 점**

프로젝트 초기 단계에서 상세한 업무 분석 자료와 개발 기준이 충분히 정리되지 않은 상태로 각 담당자가 맡은 기능의 분석과 구현을 병행했습니다.

특히 테이블 컬럼, 데이터 형식, 공통함수 등 여러 개발자가 함께 사용할 기준이 명확하게 정의되지 않아 구현을 진행하는 과정에서 수정 작업이 반복되었습니다.

대표적인 사례는 다음과 같습니다.

- **테이블 컬럼 기준:** AS-IS에서 사용하던 등록일·수정일 컬럼과 E-GENE에서 기본 제공하는 PK ID, 등록일·수정일 컬럼의 사용 기준이 정리되지 않아 개발자마다 서로 다른 컬럼을 사용하는 상황 발생
- **데이터 형식:** Y/N 값을 1/0으로 관리할지, 날짜를 년월일까지만 저장할지 시분초까지 포함할지 등에 대한 기준 미정
- **공통함수:** 여러 화면에서 공통으로 사용할 기능과 함수에 대한 정의 및 공유 부족
- **화면 구성:** 사전에 화면과 기능에 대한 충분한 분석 없이 구현을 진행하면서 기존에 구성한 화면을 변경하는 상황 반복

이러한 기준들이 개발 초기에 정리되지 않아 구현 중간에 데이터 구조와 화면을 수정해야 했으며, 테스트와 마감 일정이 가까워진 시점에는 회의를 통해 급하게 기준을 조정하고 맞춰가는 일이 발생했습니다.

**해결 과정**

- 구현 중 발견된 컬럼 및 데이터 형식의 차이를 확인하고 수정 사항 반영
- 개발자 간 논의와 회의를 통해 데이터 처리 기준 조정
- 테스트 과정에서 확인된 화면 구성 및 기능 변경 사항 반영
- 담당자들과 소통하며 공통 기준과 개별 기능의 차이를 맞춰가는 방식으로 대응

**배운 점**

이번 경험을 통해 개발 초기 단계에서 업무 및 화면 분석뿐 아니라 데이터 구조와 공통 개발 기준을 함께 정의하는 것이 중요하다는 점을 배웠습니다.

특히 여러 개발자가 동시에 작업하는 프로젝트에서는 개별 기능의 구현만큼이나 공통 컬럼, 데이터 형식, 공통함수 등에 대한 사전 합의가 중요하다는 것을 체감했습니다.

초기에 이러한 기준을 명확하게 정리했다면 개발 중간의 반복적인 수정과 화면 변경을 줄이고, 구현과 테스트에 더 많은 시간을 활용할 수 있었을 것이라고 생각합니다.

이후 개발 업무에서는 구현을 시작하기 전에 기존 구조와 데이터 기준, 공통으로 사용하는 기능을 먼저 확인하고, 필요한 사항을 팀원들과 공유하는 과정이 중요하다는 점을 배웠습니다.
