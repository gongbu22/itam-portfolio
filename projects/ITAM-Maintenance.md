# 삼성물산 ITAM 자산관리시스템 운영 및 유지보수 프로젝트

## 1. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 프로젝트명 | ITAM 자산관리시스템 운영 및 유지보수 |
| 수행 기간 | 2026.07 ~ 현재 (진행 중) |
| 담당 업무 | ITAM 전체 화면 운영 및 유지보수, 오류 분석, 데이터 관리, API 연동 로직 수정 |
| 기술 스택 | E-GENE(No-code 플랫폼), JavaScript, JSP, Java, MariaDB |
| 운영 및 분석 도구 | GitLab, OpenSearch, Argo CD, DevOpsConsole |

### 프로젝트 소개

ITAM 자산관리시스템의 운영 및 유지보수를 담당하고 있습니다.

ITSM을 통해 접수되는 요청을 바탕으로 ITAM 전체 화면의 오류를 분석하고 기능을 수정하며, 업무 로직과 데이터 처리 과정에서 발생하는 문제를 해결하고 있습니다.

기존에 직접 개발하지 않았던 기능도 담당하게 되면서 화면과 소스 코드, 데이터베이스 구조를 파악하고 현업 담당자와 협의하여 실제 업무 처리 기준에 맞게 유지보수하고 있습니다.

## 3. 주요 어려움 및 해결 과정

### 3-1. 개발 문서 부재로 인한 장애 원인 분석 및 대응 효율 개선

**어려웠던 점**

운영 업무를 인수할 당시 개발자가 시스템의 전체적인 업무 흐름과 데이터 처리 과정을 파악할 수 있는 상세 문서가 충분하지 않았습니다. 또한 시스템 안정화가 완전히 이루어지지 않은 상태에서 유지보수 업무를 시작하면서 다양한 오류가 지속적으로 발생했습니다.

초기에는 발생하는 오류를 실시간으로 처리하는 데 집중해야 했기 때문에 시스템의 전체적인 구조와 처리 흐름을 정리할 여유가 부족했습니다. 이로 인해 유사한 오류가 다시 발생하더라도 매번 관련 화면과 소스 코드, 데이터 처리 과정을 처음부터 분석해야 했으며, 장애 대응에 많은 시간이 소요되었습니다.

**해결 과정**

반복되는 오류에 보다 효율적으로 대응하기 위해 실제 처리했던 장애 사례를 유형별로 정리하고 문서화했습니다.

- 오류 발생 현상과 원인, 관련 소스 및 테이블 정보 정리
- 원인 파악을 위해 확인해야 할 데이터와 점검 순서 기록
- 오류별 조치 방법 및 수정 내용 정리
- 유사한 오류 발생 시 기존 문서를 참고하여 원인 분석 및 대응

처음 문서화하는 과정에는 추가 시간이 필요했지만, 이후 유사한 오류가 발생했을 때 기존 분석 내용과 조치 방법을 참고할 수 있어 반복적인 소스 분석을 줄이고 보다 신속하게 대응할 수 있었습니다.

**배운 점**

이번 경험을 통해 운영 업무에서는 당장의 오류를 해결하는 것뿐 아니라, 문제를 해결하는 과정과 결과를 체계적으로 기록하는 것도 중요하다는 점을 배웠습니다.

특히 개발 문서가 부족한 환경에서는 담당자가 직접 분석한 내용을 문서화하고 축적하는 것이 이후 장애 대응의 효율성을 높이는 데 도움이 된다는 것을 경험했습니다.

또한 개인이 파악한 시스템 지식과 문제 해결 방법을 문서로 남겨두는 것이 지속적인 시스템 운영과 유지보수의 기반이 될 수 있다는 점을 체감했습니다.

### 3-2. SAP API 연계 과정에서의 데이터 검증 및 유관 담당자 간 소통

**어려웠던 점**

ITAM에서 자산 관련 품의서를 생성하기 위해 SAP API를 호출하는 기능을 유지보수하면서 인터페이스 정의서와 테스트 환경 간의 차이로 인해 원인 분석 및 검증에 어려움이 있었습니다.

- **인터페이스 정의서의 정보 부족:** 필수 요청 파라미터가 명확하게 구분되어 있지 않았고, 요청 및 응답 데이터 예시도 충분히 제공되지 않아 API 호출에 필요한 정보를 파악하기 어려웠습니다.
- **환경별 데이터 불일치:** 개발·품질·운영 환경의 SAP 데이터와 ITAM 자산 데이터가 서로 달라 동일한 조건으로 API 호출을 테스트하기 어려웠습니다.
- **오류 기준 및 응답 정보 부족:** SAP 호출 실패 시 발생하는 오류 유형과 처리 기준이 명확하게 정의되어 있지 않아 오류 원인을 판단하고 후속 처리 방식을 확인하는 데 어려움이 있었습니다.

특히 품질 환경에서 테스트할 수 있는 자산을 찾기 위해 SAP 담당자에게 확인을 요청하는 과정도 있었지만, 환경별 데이터 차이와 제한 사항으로 인해 테스트 대상을 확보하는 데 한계가 있었습니다.

**해결 과정**

API 호출 오류와 데이터 불일치를 파악하기 위해 로그와 인터페이스 관련 데이터를 함께 확인하며 원인을 추적했습니다.

- OpenSearch 로그를 통해 API 호출 시 발생한 오류와 응답 내용 확인
- 인터페이스 정보를 저장하는 테이블의 데이터를 조회하여 요청 파라미터 및 응답 데이터 확인
- 필수 파라미터 누락이나 데이터 불일치가 의심되는 경우 현업 담당자에게 확인을 요청하고, 현업 담당자와 SAP 담당자 간 추가 확인 및 협의가 이루어질 수 있도록 소통
- 정의되지 않은 SAP 호출 오류와 처리 기준에 대해 관련 담당자에게 확인 요청

또한 SAP API의 정상 응답을 기반으로 한 후처리 기능을 검증할 때는 실제 SAP 호출 테스트가 어려운 환경적 제약을 고려하여, 정상 응답 형태의 JSON 데이터를 임의로 구성해 테스트 데이터로 활용했습니다. 이를 통해 응답 데이터에 따른 Java 후처리 로직을 수정하고 기능 동작을 확인했습니다.

**배운 점**

이번 경험을 통해 외부 시스템과 API를 연계할 때는 단순히 요청과 응답을 주고받는 것뿐 아니라, 인터페이스 정의서의 정확성, 환경별 데이터 정합성, 오류 처리 기준까지 함께 확인해야 한다는 점을 배웠습니다.

또한 연계 시스템의 데이터와 처리 기준을 개발자가 단독으로 파악하기 어려운 경우가 많기 때문에, 현업 담당자 및 외부 시스템 담당자와의 원활한 소통이 문제 해결에 중요한 역할을 한다는 것을 경험했습니다.

특히 로그와 인터페이스 데이터를 근거로 문제 상황을 구체화하고, 확인이 필요한 사항을 정리해 유관 담당자에게 전달하는 것이 효과적인 장애 대응의 중요한 과정임을 배웠습니다.
